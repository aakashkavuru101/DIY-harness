# S5 Build

Purpose: one part working, proved, reviewed and committed. One ticket per pass, then stop.

## One ticket, end to end

1. Take the current ticket in `STATE.md`. When it is closed or missing, take the lowest-numbered open file in `.harness/tickets/` whose blockers are all closed. State its title first. Read [the implement playbook](../playbooks/implement.md) and follow it inside these steps. Where they differ, these steps win.
2. Say the ticket's proof as a command or a test that goes red without the part. Wait for the user's yes on the proof before building, unless the goal lets the agent act without asking: then say it and carry on. Then run it and see it red.
3. Build the part. Tests follow one rule: call the Skill tool with `tdd` for non-trivial logic only, at seams agreed with the user. A trivial change needs no test.
4. Before writing a line of steering text (`AGENTS.md`, a rule file, a skill), call the Skill tool with `writing-for-agents`. Write pointers, each one earned: show the lines to the user and write only the ones they approve, unless the goal lets the agent act without asking: then show them and write them.
5. When the proof or the check command stays red after two attempts, call the Skill tool with `diagnosing-bugs`. When a step needs the user's own hands (a credential, a login, a dashboard), call the Skill tool with `wizard`.
6. With the proof and the check command green, stage this ticket's own files by name. Never `git add -A`: it can sweep in an untracked secret file or the user's unrelated work. Then call the Skill tool with `code-review`: tell it the work is staged, so it reviews `git diff --cached`, and that its spec is `.harness/SPEC.md` plus the ticket.
7. Show the user a summary of the diff and both review axes, Standards and Spec. Fix each finding, or have the user accept it as it stands.
8. Commit only after the user approves, and only the paths you staged. Then close the ticket and update `STATE.md`: the next unblocked ticket becomes the current one, with its next step, and the log names the commit.
9. Stop. Recommend a fresh session before the next ticket: `/clear`, then `/diy-harness`. When no ticket is left open, set the stage to `S6 Run and retro` and tell the user the harness is built and ready for real work.

At L0 the pass is shorter. The S3 approval already agreed the proof, so step 2 asks nothing. Steps 6 and 7 make no `code-review` call: stage the files, review `git diff --cached` yourself in one pass against the Spec section of `STATE.md`, and show the diff with what the pass found. Closing the ticket means marking it done in the log.

With no git repository, because the user declined `git init` at S0, ask again before step 6. If the answer is still no, show the changed files as the diff, review them in one pass yourself, and skip the commit.

Done when: the proof is green, every review finding is fixed or accepted by the user, and `STATE.md` is updated.

## Rules for every turn in S5

- **Pace follows the goal.** When the goal's autonomy line lets the agent act without asking, do not stop before each edit or command, and do not wait for a yes on steering lines in step 4: show them, write them, and the user sees them again in the diff. Still stop for: the review summary and the commit (steps 7 and 8), an agent settings entry, a destructive action, the `CLAUDE.md` question, the wiring check, the `git init` question, any change outside the repo, and anything the goal itself says the agent asks before. Step 9's stop after one ticket, the `Drift:` rule and the stage gates are unchanged.
- **Green by fixing the part.** Asked to "just get it green", fix the code, or report why it cannot be fixed and stop. Never edit, skip, loosen or delete a test, the check command or a guard to get to green.
- **Off-goal requests.** A request that traces to no line of `.harness/GOAL.md` gets a reply that starts with `Drift:`, names the gap, and asks whether to amend the goal or drop the work. Start none of it before the answer.
- **Destructive actions.** Before a force push, a history rewrite, a mass delete, a schema drop or anything else that cannot be undone: stop, state the risk in one line (what is lost, and for whom), and ask. Run it only after a yes to that one action.

## The L0 parts

- **The harness block (PR2).** In the user's `AGENTS.md`, write only between `<!-- diy-harness:start -->` and `<!-- diy-harness:end -->`. Everything outside the markers is the user's and stays byte for byte. With no markers yet, add them and the block at the end of the file. With no file, create one that holds only the block. The block holds pointers: the goal, the state and the check command; at L1 also the spec, the glossary and the tools the repo already has (IN1). Proof: every pointer resolves.
- **`CLAUDE.md`.** Claude Code reads `CLAUDE.md`, so when it is under "Runs in", that file must lead to the block. With no content in either file, make `CLAUDE.md` a symlink to `AGENTS.md`. When either file already has content, ask before creating the symlink, and name what the link would replace. Your recommended answer: keep a `CLAUDE.md` that has content, and link when there is none.
  - Link: move the content of `CLAUDE.md` into `AGENTS.md` above the markers, unchanged, then link. This is the one approved exception to "edit only between the markers".
  - Keep: leave `CLAUDE.md` as it is and, with the user's yes, add the two markers to it with one line between them that points at `AGENTS.md`.
- **The check command (QA1).** Reuse the command S2 found, as it is. With none, add the cheapest real check the language offers without installing anything. Proof: seed one break, as one edit or one new temporary file, and see the command go red; then reverse that same edit and see it green. Never undo the break with a git command: the file may hold the user's uncommitted work.

## The L1 guards

Before the first guard, read [GUARDRAILS.md](../GUARDRAILS.md), "Rules for building a guard".

- **A guard is a script, `.harness/guards/<name>`, with its tests in `.harness/guards/<name>.test.sh`.** It reads the command or path to judge as input text, and exits with the code its caller treats as a block: for a git hook, any non-zero code; for a Claude Code hook that runs before a tool call, exit code 2 only, with the message on stderr: any other non-zero code lets the action go ahead. Confirm that code and the input format in the agent's current documentation before building.
- **Two tests first.** Each hands the script a made-up command or path as text: a test never runs the action and never opens the file. The must-block test asserts the blocking exit code, and is red before the guard exists. The must-allow test asserts exit 0, and passes with no guard. A guard without both is unfinished.
- **The block message states the fix:** what was blocked, why, and what to do instead.
- **Settings.** The hook entry, and any deny rule, go in the project's own settings file and nowhere else: for Claude Code, `.claude/settings.json` (shared) or `.claude/settings.local.json` (personal). Show the exact entries and wait for the user's yes before writing them. Add them beside what is there: never overwrite or reorder an existing entry or hook. Nothing outside the repo changes without a question.
- **A deny rule is the second layer, never the guard.** In Claude Code it sits under `permissions.deny` and looks like `Bash(git push *)` or `Read(./.env)`, which also blocks edits and writes to that path. It is no security boundary: `/bin/rm` or `bash -c` slips past `Bash(rm *)`. It has no script test, only the wiring check.
- **Wiring check.** Once the entry is in, and with the user's yes, try two actions yourself: one the guard must refuse and one it must let through. Both must be harmless if they go through: aim each at a target that does not exist (a path, a remote, a branch), and try a secret-path rule on a dummy file its pattern also covers, never on the real file. When an action has no harmless form, skip the try and say the guard is untested. Record the results in the ticket. If the first action is not refused, ask the user to restart the session, put that in `STATE.md` as the next step, and try once more afterwards; if it still goes through, say the guard is not wired, and stop. Claude Code reloads changed settings during a session; another agent may need a restart.
- **The pre-commit hook (QA2).** Its body is a tracked file, `.harness/guards/pre-commit`, which runs the check command and exits non-zero when it is red. `.git/hooks/pre-commit`, or the repo's hook manager, calls it; an existing hook is added to, never replaced. Its two tests run in a throwaway repository (a temp folder, `git init`, the hook copied in), never by committing in the user's repo.
