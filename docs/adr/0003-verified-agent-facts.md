Rows H1 to H5 are the Claude Code hook facts that ticket 07 relies on (M2). Each is quoted from the Claude Code docs
(code.claude.com/docs/en/hooks and /plugins/manifest-reference, read 2026-11-16; the pages are not pinned to a
version). The installed CLI is 2.1.325. "Docs" in the Result column means read in the docs; "Observed" means seen in a
run on 2.1.325.

| Item | Fact | Version checked | Result | Enforced by |
| --- | --- | --- | --- | --- |
| H1 | `SessionStart` output format | Docs; observed on CLI 2.1.325 | Docs: "Claude Code adds a SessionStart hook's plain-text stdout to Claude's context." The hook prints plain text. Observed 2026-11-16 in one `claude -p --plugin-dir` run: the main agent quoted all three header lines | `tests/check.test.sh` (hook output) |
| H2 | `SubagentStart` output format | Docs; observed on CLI 2.1.325 | Docs: `SubagentStart` "can inject context into the subagent" through `hookSpecificOutput.additionalContext`. The docs list the events whose plain stdout reaches Claude as "`UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, and `PostModelSwitch`"; `SubagentStart` is not among them, so the hook prints JSON. Observed in the same run: a dispatched subagent quoted the ponytail and i-have-adhd headers, and not the agreement header | `tests/check.test.sh` (JSON shape) |
| H3 | Cap on one hook's output | Docs; CLI 2.1.325 | Docs: "A hook's `additionalContext`, `systemMessage`, and `initialUserMessage` strings, and its plain stdout, are capped at 10,000 characters." Longer text goes to a file, and Claude gets the path and a preview of up to 2,000 characters. Hence one run per rule set (PLAN.md Q7). Observed: the parts can arrive in any order. That run showed agreement, then i-have-adhd, then ponytail, so the precedence must be stated in words (ticket 10) | `scripts/check.sh` budget check, 10,000 bytes per part |
| H4 | `hooks/hooks.json` loads automatically | Docs; CLI 2.1.325 | Docs, manifest reference: "Claude Code merges whatever you declare with `hooks/hooks.json` when that file exists." `claude plugin validate . --strict` passes on 2.1.325 with or without a manifest `hooks` entry, so it does not show double registration. Observed: the live `--plugin-dir` run loaded `hooks/hooks.json` with no manifest entry. The entry is left out (PLAN.md Q8, ADR 0002) | `scripts/check.sh` hooks-wiring check |
| H5 | `timeout` and failures | Docs; CLI 2.1.325 | Docs: `timeout`: "Seconds before canceling". The default is "600 for `command`, `http`, and `mcp_tool`". The session-start entries set `timeout: 10` and the prompt tracker sets `timeout: 5` | `tests/check.test.sh` (hooks.json wiring) |

Rows H6 to H8 are the session facts ticket 08 relies on. They were observed on 2026-11-16 in three
`claude -p --plugin-dir` runs on CLI 2.1.325, approved by Aakash, costing an estimated $1.09 in plan usage. All three
ran in one throwaway project whose `.claude/settings.json` set `DIY_HARNESS_OFF` to `adhd`: "stop ponytail" with
`--session-id`, then `--resume` with a subagent, then `--resume` with `/compact`.

| Item | Fact | Version checked | Result | Enforced by |
| --- | --- | --- | --- | --- |
| H6 | The session ID across resume, compaction and `/clear` | Docs; observed on CLI 2.1.325 | Docs: `CLAUDE_CODE_SESSION_ID` "matches the `session_id` field in the hook JSON input and is updated on `/clear`", and "On `--resume <session-id>` it receives the resumed ID". Observed: the tracker's flag was named by the `--session-id` value; both resumed runs reported the same ID; after `/compact` the ID was unchanged, and the `SessionStart:compact` hook printed the ponytail off notice again. `/clear` was not run (print mode); by the docs it starts a new ID, so a session switch ends there, and the README and the tracker's message say so | `tests/check.test.sh` (flags keyed by session ID) |
| H7 | `SubagentStart` input carries the parent's session ID | Docs; observed on CLI 2.1.325 | Docs list `session_id` as a common input field. | H8 | Hooks see `env` from a project's `.claude/settings.json` | Docs; observed on CLI 2.1.325 | Docs: "A hook process inherits the parent environment", and an `env` block in a settings file "follows the levels above"; they do not say outright that hooks get it. Rows R1 to R8 are the facts ticket 09's eval runner relies on. They were observed on 2026-11-16 on CLI 2.1.325, with
the model `claude-sonnet-5-5` (the setup token's default), in `evals/live-checks.sh` runs and five probes. All
together they cost about $1.50 in plan usage. The docs quoted are code.claude.com/docs/en/env-vars and
/permissions, read 2026-11-16.

| Item | Fact | Version checked | Result | Enforced by |
| --- | --- | --- | --- | --- |
| R1 | `--safe-mode` | CLI help 2.1.325 | Help: "Start with all customizations (CLAUDE.md, skills, installed plugins, hooks, MCP servers, custom commands and agents, ...) disabled". It would switch off the always-on hooks that the evals test, so the runner does not use it. Whether it also drops a `--plugin-dir` plugin was not checked | `tests/test_evals.py` (flags) |
| R2 | `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` | Docs; observed on CLI 2.1.325 | Docs: it strips credentials "from the environments of the subprocesses Claude Code starts, such as Bash commands, hooks, and stdio MCP servers". Its table says `CLAUDE_CONFIG_DIR`: "Removes it". A hook in a trial therefore falls back to `$HOME/.claude`, so the runner makes `HOME` throwaway too. Observed: in smoke-env the agent's `env` showed neither `CLAUDE_CODE_OAUTH_TOKEN` nor `CLAUDE_CONFIG_DIR`, and showed the throwaway `HOME` | `tests/test_evals.py` (env), smoke-env |
| R3 | `CLAUDE_CODE_OAUTH_TOKEN` | Docs; observed on CLI 2.1.325 | Docs: it "Takes precedence over keychain-stored credentials" and is "Ignored in project and local settings". Observed: trials with an empty config folder signed in with it. `evals/README.md` therefore sets it for each eval command only, never in a shell profile | `evals/README.md` |
| R4 | Cost and budget across `--resume` | Observed on CLI 2.1.325 | After `--resume`, `total_cost_usd` covers the whole session: turn 2 reported $0.0829, which is turn 1's $0.0422 plus its own $0.0407, and `modelUsage` adds up the same way. `--max-budget-usd` holds only the call's own cost: a resumed call with a $0.03 budget succeeded at a session total of $0.0399, of which $0.0158 was its own. The budget is checked after each API call, so a call can overshoot: a $0.01 budget stopped at $0.043 with subtype `error_max_budget_usd`. The runner therefore starts no call unless what is left covers the dearest call so far | `tests/test_evals.py` (stand-in CLI: cost, ceiling) |
| R5 | Permission mode in `-p` | Observed on CLI 2.1.325 | `--permission-mode acceptEdits` was reported as `default` in the `init` event in two cases. One is a folder that no `.claude.json` trust record covers. The other is any folder whenever `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` is set, trusted or not and even through `--settings`; in both cases every Write was refused. `plan` mode was kept. The docs say nothing about either case. A flag rule, `--allowedTools "Edit(//<folder>/**)"`, works under the scrub: Write created a file in the folder and was refused one folder up. The runner uses that rule, which is the ticket's "explicit tool list" route. It also denies `Edit(//<folder>/.claude/**)`, because the next `--resume` would load settings the agent wrote there. It denies the tools the `init` event lists that act outside the folder (`RemoteTrigger`, `CronCreate`, `CronDelete`, `ScheduleWakeup`, `Workflow`, `SendMessage`, `ListAgents`), without probing whether each would have asked first. Those seven then drop out of the `init` tool list, and `evals/live-checks.sh` fails when a trial gets a tool outside the 16 that were reviewed | `tests/test_evals.py` (allow rule), smoke-two-turn |
| R6 | `claude -p` output and flags | Observed on CLI 2.1.325 | `--verbose --output-format stream-json` emits an `init` event (model, cwd, `permissionMode`, plugins, `slash_commands`), assistant events with `tool_use` blocks, and a closing `result` event. `--` ends the options, so the prompt comes after variadic options such as `--allowedTools`. `--session-id` and then `--resume` keep the context: smoke-two-turn's turn 2 knew turn 1's code word. `--permission-prompts none` refuses whatever would prompt. A `--plugin-dir` plugin loads as `diy-harness@inline`, next to Claude Code's built-in plugins `cc-plugin-agents-md`, `cc-plugin-privacy` and `cc-plugin-plugin-authoring`, which the runner leaves on. With no `--`, the prompt is read from stdin; the judge call uses that | smoke cases |
| R7 | `/diy-harness` typed as a `-p` prompt (part of item 4b) | Observed on CLI 2.1.325 | With the plugin loaded through `--plugin-dir`, the `init` event lists only the namespaced form `diy-harness:diy-harness`. Yet the E4 prompt `/diy-harness` reached the parent stub: the agent restated the stub's text and called it `/diy-harness:diy-harness`. Typing the command in an installed plugin is still M4's check | E4 |
| R8 | The shape of a Skill call and a subagent dispatch | Observed on CLI 2.1.325 | In smoke-skill-subagent, a plugin skill call was `{"name": "Skill", "input": {"skill": "diy-harness:grilling"}}`, namespaced by the plugin. The dispatch was a `tool_use` named `Agent`, with `description`, `prompt` and `subagent_type`, although the `init` event's tool list names it `Task`. So the graders match `(^|:)grilling$` and `Task\|Agent`. The trimmed events are `tests/fixtures/evals/skill-and-subagent.jsonl` | `tests/test_evals.py` (recorded stream) |
