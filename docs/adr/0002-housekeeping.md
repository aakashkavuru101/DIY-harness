| Hook wiring (2026-11-16, `PLAN.md` Q8) | `.claude-plugin/plugin.json` has no `hooks` entry; `hooks/hooks.json` is loaded by convention. This departs from document 05 section 3, which lists a `hooks` field pointing at `hooks/hooks.json` | The Claude Code plugin manifest reference: "Claude Code merges whatever you declare with `hooks/hooks.json` when that file exists", so naming it may register every hook twice; upstream i-have-adhd ships without the entry. The doc quote and CLI version go in ADR 0003 with ticket 07 |
| Resume (2026-11-19, decided by Aakash) | When `.harness/STATE.md` exists, `/diy-harness` resumes in the same reply, with no confirm turn: it carries on with the next step of a built stage, and for a stage not built yet it reports and stops. The stage gates are unchanged, with one effect to know: the S1 gate sets `STATE.md` to S2 and then asks "start S2?", so a later `/diy-harness` starts S2 without asking again; typing the command counts as the yes. This departs from document 04 section 3, S0 step 1 ("continue there after the user confirms"), and from the Q5 reading of E4 in `PLAN.md` ("offers to continue ticket 03 and waits"). In M2, with S5 not built, E4 passed when the reply named stage S5, ticket 03 and its next step, said the stage was not built yet, and started no work; in M3, with S5 built, E4 returned to document 06's "continues ticket 03" | The agent ran ahead of the confirm turn in about one resume in three, through four rewordings of that step (`tickets/13-s2-assess-and-level.md`) |
| Levels (2026-11-19, decided by Aakash) | When a part's trigger counts as fired is in `references/LEVELS.md`, "Minimal by default". A rule the goal only states (a "never" line, an autonomy line that has the agent ask before commands, only lets it edit files, or says nothing about commands) stays at L0 until it is broken or the user asks for enforcement. Three safety facts fire without a failure: a secret in reach (IN6), a destructive command the work needs (PR6), and an autonomy tier that lets the agent run commands without asking each time, the tests included (PR7 and the sandbox IN7, so at least L2). The ponytail ladder can show such a part is already there, never that the fact needs no part. Document 07 section 5 also lists IN6, QA1 and PR8 for such a tier; this ruling adds only PR7 and IN7. This settles a conflict between document 04 section 3 (S1 always asks for an autonomy tier), document 02 section 4 (PR7 at L1, earned by "more than read-and-ask") and document 06 section 4 (E1 "proposes L0"). E1 passed at L0 or at L2, whichever fitted the autonomy line in the approved goal, until D14 was confirmed on 2026-11-20; since then S1 recommends tier B and E1 expects L0. Two rulings added the same day, after a third review: a tier that lets the agent run some commands without asking and has it ask before others (a delete, a commit, a file outside the repo) is such a tier, so at least L2; and when a sandbox is already switched on the level is still L2, with IN7 listed as already there. `LEVELS.md` states both since M3 | The first reading (catalogue triggers as written) gave L1 for a one-script harness; the second (every stated rule stays L0) left command-running tiers with no sandbox even mentioned, against document 07 section 5 |
| Skipped goal (2026-11-19, decided by Aakash) | After "just do it" at the S1 gate, `GOAL.md` is headed `# GOAL (approval skipped <date>)` and later rules treat it as the goal. Document 04 section 6 only says to record the skip in the `STATE.md` log | The file otherwise looks approved, though it can hold recommended answers the user never saw |
| Status (2026-11-19, decided by Aakash) | `/diy-harness status` lists every open decision as `STATE.md` words it and invites no answer; its first line says to run `/diy-harness` to continue. This is what "it asks nothing" in the parent skill means. The parent skill says so since M3 | In the proving run all three `s0-status-s1` trials told the user to answer the open decisions (one: "Answer the two open questions below (reply "yes" to take both recommendations)"), as a resume's own grilling round does, and the case passed them |
| Departures in M3 (awaiting Aakash) | The S3 to S5 text departs from the spec in six places. Aakash has not decided on any of them yet. (1) L0 fast path: at L0, S3 is one reply whose approval is also the spec approval and S5's proof agreement, and S5 reviews the diff in one inline pass, not with the two-subagent `code-review` (document 04 section 3, S5 steps 2 and 7, has no L0 exception). (2) A part above L1 that the user insists on is recorded as an override and not built (document 04 section 6 says to build it); case E5 grades this, against document 06 section 4. (3) No eval case first for a prose part at L0 and L1: the user approves each steering line (document 04 S5 step 3, and the last clause of D4, "prose parts are proved by evals"). (4) An existing `CLAUDE.md` with content: document 04 section 6 says to keep it, add the harness block between markers, and ask before creating the symlink. The text keeps it by default too, but with the user's yes it gets one pointer line between the markers, not the block; and if the user chooses the link, its content moves into `AGENTS.md` above the markers, the one write outside the markers the text allows. (5) A part that answers a safety fact still counts toward the level when it is already there: the "Levels" row says this for the sandbox, the text says it for every safety fact. (6) The failure log (KN8) is parked until S6, though document 02 section 4 lists it at L1 | (1) Document 02 section 3: the build process runs "at every level, scaled down at L0", whose ceremony per change is "Goal, build, one check". (2) M3 builds L0 and L1 only. (3) `.harness/evals/` is an L3 part (document 04 section 4). (4) It protects a file the user wrote. (5) It follows the "Levels" ruling. (6) Document 04 section 4 has `FAILURES.md` written in S6 |
